Area 1 — sys_genesis_invoke and GENESIS_CAP Semantics
Current state: GENESIS_CAP is an inert typed token. It is inserted into userspace cspace slot 1 and published in bootinfo, but there is no syscall path keyed off CAP_TYPE_GENESIS. The current userspace binary only checks that bootinfo->genesis_cap_slot == 1 and never uses it.
Required end state: GENESIS_CAP has real semantics enforced by the kernel. A new syscall sys_genesis_invoke is callable only by the holder of a CAP_TYPE_GENESIS capability. It supports exactly three operations:

GENESIS_OP_SPAWN — create a new process from a module descriptor. Takes a module index from bootinfo, creates a new address space, loads the ELF, maps the stack, injects an initial capability set, and queues the first thread. Returns the new process's PID and initial capability handles to the caller.
GENESIS_OP_DELEGATE — mint a specific authority directly into a target process's capability slot, bypassing the caller's own capability logic. This is the mechanism that allows Genesis to hand the audit write capability directly to Sentinel's process without routing it through Paradigm's core capability list.
GENESIS_OP_DESTROY — irrevocably destroy the GENESIS_CAP. After this operation, no process can invoke sys_genesis_invoke ever again. The kernel must enforce this permanently — not just for the current session.

The GENESIS_OP_DESTROY operation must be the last thing Genesis calls before exiting. After it returns, the kernel must mark the GENESIS_CAP type as permanently exhausted so that even if someone manufactured a fake CAP_TYPE_GENESIS token, the syscall path would reject it.
Done condition: A boot marker [GENESIS] sys_genesis_invoke: PASS appears in serial.log from a kernel self-test that verifies all three operations are callable with a valid GENESIS_CAP, that GENESIS_OP_DESTROY makes subsequent invocations fail, and that a non-GENESIS_CAP holder cannot invoke the syscall at all.
